## 5. Existing System Analysis

### 5a. Version flow (confirmed by direct inspection)

`pubspec.yaml` (`version: X.Y.Z+B`) is the **single declared source of truth**. Every
other file either reads it dynamically at build/run time or is a generated,
git-ignored artifact — **except** `web/version.json`, which is a second, independently
committed source that must be kept in sync manually.

| File | Mechanism | Type |
|------|-----------|------|
| `pubspec.yaml` | Declares `version: 1.4.1+232` directly | **Source of truth** |
| `web/version.json` | Committed JSON (`version`, `build_number`) polled by `VersionCheckService` at runtime to detect stale PWA sessions and force-reload | **Second source of truth — must be kept in sync manually** |
| `ios/Runner/Info.plist` | `CFBundleShortVersionString` = `$(FLUTTER_BUILD_NAME)`, `CFBundleVersion` = `$(FLUTTER_BUILD_NUMBER)` | Reads dynamically (Flutter build injects from `pubspec.yaml` via `ios/Flutter/Generated.xcconfig`, git-ignored) |
| `ios/Runner.xcodeproj/project.pbxproj` (Runner target) | `CURRENT_PROJECT_VERSION = "$(FLUTTER_BUILD_NUMBER)"` | Reads dynamically |
| `ios/Runner.xcodeproj/project.pbxproj` (RunnerTests target) | `CURRENT_PROJECT_VERSION = 1; MARKETING_VERSION = 1.0;` | Xcode-generated test-target defaults, unrelated to the shipped app version, not user-facing |
| `macos/Runner/Info.plist` | `CFBundleShortVersionString` = `$(FLUTTER_BUILD_NAME)`, `CFBundleVersion` = `$(FLUTTER_BUILD_NUMBER)` | Reads dynamically |
| `macos/Runner.xcodeproj/project.pbxproj` (RunnerTests target only) | `CURRENT_PROJECT_VERSION = 1; MARKETING_VERSION = 1.0;` | Same as iOS — test-target defaults, unrelated |
| `android/app/build.gradle.kts` | `versionCode = flutter.versionCode`, `versionName = flutter.versionName` | Reads dynamically from `android/local.properties` (git-ignored, regenerated by Flutter tooling from `pubspec.yaml` on every build — confirmed current local value already reads `flutter.versionCode=232`) |
| `lib/app/services/app_version_service.dart` | `PackageInfo.fromPlatform()` | Fully dynamic, no hardcoded value or independent source |
| `lib/app/services/version_check_service.dart` | Fetches `/version.json` at runtime, compares to `AppVersionService.buildNumber` | Consumes `web/version.json`; declares no version itself |
| `marketing/changelog.html` | Static Webflow marketing page with placeholder text `Version_01.0` | Unrelated static content, not the shipped app version, out of scope |

### 5b. How the deploy pipeline treats version.json
`tools/deploy_web.sh` (lines 147–199) auto-increments the build number by 1 on every
production deploy: it parses `pubspec.yaml`, computes `build = current_build + 1`,
rewrites `pubspec.yaml`, regenerates `web/version.json` from the same values, then
commits both together with message `chore: bump build version` and pushes to `main`.
This exactly matches the message and file pair seen in the last 5 version-bump commits
in git history (`f141873`, `5fa68b5`, `ca5675a`, `6ac4f61`, …), confirming those were
produced by running this script, not by manual edits. The script only auto-increments
the **build** number — it never changes the semantic `X.Y.Z` version. A semantic bump
(1.4.1 → 1.4.2) requires a manual edit, which is what this chore performs.

### 5c. Discrepancy vs. Feature Input
The Feature Input states "Previous version was 1.4.1+231." Direct inspection of
`pubspec.yaml` on up-to-date `origin/main` (`a98b548`) shows the actual current value is
**`1.4.1+232`**, not `+231`. History shows `+231` was reached and briefly re-confirmed
via commit `b06ffdb` ("chore: resolve version conflict, keep 1.4.1+231"), then bumped
again to `+232` by `f141873` on 2026-07-27, prior to the PR #88 merge. `web/version.json`
is consistent with `pubspec.yaml` at `232` — there is no cross-file divergence between
Android/iOS/web, and `AppVersionService` has no independent source. This does **not**
meet the plan's stop-condition bar (which is specifically about platform files
disagreeing with each other, or `AppVersionService` carrying its own out-of-sync value).
It is purely the Feature Input's stated starting point being stale by one prior bump.
Proceeding with target `1.4.2+233` — build `233` is still strictly greater than the
actual current build `232`, so monotonicity for store submissions is preserved.

## 6. Proposed Solution
Manually edit the two files that declare a version value directly:
1. `pubspec.yaml` — `version: 1.4.1+232` → `version: 1.4.2+233`
2. `web/version.json` — `"version": "1.4.1"` → `"1.4.2"`, `"build_number": "232"` →
   `"233"`, matching the exact field shape the deploy script itself generates.

No other file is edited. iOS, macOS, and Android all resolve their version at build
time from `pubspec.yaml` via Flutter tooling (through git-ignored generated files),
so a `pubspec.yaml` edit alone propagates to all four affected platforms (iOS,
Android, Web, macOS) without any platform-specific file changes.
