# Architect Plan — bug/rls-migration-comment-escaping

## Feature Slug

`bug/rls-migration-comment-escaping`

## Problem Summary

`supabase/migrations/20260823120000_wrap_rls_auth_functions.sql` (merged to `main` at commit `281e1d9` via PR #176, but never applied to any database) contains 474 unprefixed continuation lines within inline documentation comment blocks. The file documents each RLS policy change with `-- Old WITH CHECK:` / `-- Old USING:` / `-- New ...:` comment headers, each followed by the full multi-line captured policy definition text. The comment-generation script that produced this file only prefixed the *first* line of each such block with `--`; every continuation line is unprefixed, causing Postgres to parse them as literal SQL statements sitting outside any policy definition. This aborts `supabase db push --linked` with a syntax error the moment it reaches the first such block (line 64).

Example of malformed comment block (lines 63-65):

```sql
-- Old WITH CHECK: ((EXISTS ( SELECT 1
   FROM band_members
  WHERE ((band_members.band_id = band_invitations.band_id) ...
```

Lines 64-65 have no `--` prefix, so Postgres interprets `FROM band_members` as a bare SQL fragment and rejects the file.

## Root Cause

**Cause:** Automated migration-generation script that produced `20260823120000_wrap_rls_auth_functions.sql` emitted multi-line policy definition text in inline comments but only prefixed the first line of each comment block with `--`, leaving 474 continuation lines unprefixed across the file's 1938 lines.

**Mechanism:** When `supabase db push` attempts to apply the migration, Postgres's SQL parser encounters unprefixed lines like `   FROM band_members` and `  WHERE ((band_members.band_id = ...` outside any statement context and rejects the file with a syntax error. The transaction rolls back cleanly — confirmed via live `supabase db query` showing `auth_rls_initplan` still at 124 warnings (unchanged) and migration ledger showing this file was never recorded as applied.

**Confidence:** `HIGH` — confirmed via direct file inspection showing 298 comment header lines (`-- Old USING:` / `-- New USING:` / `-- Old WITH CHECK:` / `-- New WITH CHECK:`) followed by 474 unprefixed continuation lines, reproduced via `awk` pattern matching, and verified via terminal history showing `supabase db push` failures with syntax errors in exactly this file.

### Comment Block Pattern (Malformed)

Example from lines 63-68:

```sql
-- Policy: Admins can create invitations
-- Old WITH CHECK: ((EXISTS ( SELECT 1
   FROM band_members
```

Lines 64-65 and 67-68 lack `--` prefix. This pattern repeats for all 126 policies wherever the USING/WITH CHECK clause spans multiple lines in Postgres's internal representation.

### Why This Exists

The migration file was generated by an automated script that captured each policy's definition via `pg_policies.qual` and `pg_policies.with_check`, which returns multi-line formatted SQL from Postgres. The script emitted these as inline documentation comments but only prefixed the first line with `--`, assuming the text was single-line. The multi-line structure of complex policies (those with EXISTS subqueries, multiple AND clauses) broke that assumption.

## Solution Design

### Approach

Regenerate each `-- Old USING:` / `-- New USING:` / `-- Old WITH CHECK:` / `-- New WITH CHECK:` comment block to collapse the policy definition text to a single line instead of preserving the multi-line format from Postgres's internal representation. This eliminates all continuation lines, ensuring every line in the file is either a valid SQL statement or a properly prefixed comment.

### Transformation Pattern

**Before (malformed):**

```sql
-- Old WITH CHECK: ((EXISTS ( SELECT 1
   FROM band_members
  WHERE ((band_members.band_id = band_invitations.band_id) ...
```

**After (corrected):**

```sql
-- Old WITH CHECK: ((EXISTS ( SELECT 1 FROM band_members WHERE ((band_members.band_id = band_invitations.band_id) ...
```

All whitespace (newlines, indentation) within the captured policy definition is collapsed to single spaces, keeping the entire text on one line following the `-- Old ...:` or `-- New ...:` prefix.

### Rationale

- The inline comments are for human reference only (explaining what changed). The complete pre-migration definitions already exist in `PRE_MIGRATION_RLS_STATE.md` for rollback purposes, so shortening the inline comments loses no information.
- Collapsing to single lines is simpler and safer than correctly prefixing every continuation line with `--`, which would require parsing SQL structure to identify line boundaries.
- The actual `CREATE POLICY` statements are unaffected — they remain multi-line as emitted by the script, which is correct PostgreSQL syntax.

### Out of Scope

- No changes to `20260823120001_harden_get_user_band_role_search_path.sql`
- No changes to any `CREATE POLICY` or `DROP POLICY` statement (transformation logic is correct)
- No changes to policy logic (USING/WITH CHECK clauses remain byte-for-byte identical to the original design)
- No changes to `search_path` values in either migration file
